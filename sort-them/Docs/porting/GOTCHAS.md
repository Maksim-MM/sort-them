# Cross-stage подводные камни (porting pipeline)

> Часть porting-пайплайна. Индекс, маршрутизация и порядок чтения — `PORTING_PIPELINE.md` в этой папке.
> Читать перед любой работой с префабами/сценами через Unity MCP — на любой стадии.

> ⚠️ **Первым делом при работе через Unity MCP — закрепить инстанс** (`set_active_instance` по `Name@hash`, не по порту): у разработчика бывает открыто несколько окон Unity, без пина вызовы уходят в чужой проект недетерминированно. Полный протокол старта — `MCP_REFERENCE.md`.

> ⚠️ **Подводный камень: сборка на сервере падает с `CS0234`, хотя на ноуте всё компилируется.** Две разные причины, обе про пакеты (словлено на первой PS5-сборке):
> 1. **`.gitignore` глотает исходники пакета.** Правило `[Bb]uild/` (для выходных билдов Unity) матчит **любую** папку `Build/` в репо — в т.ч. `Packages/com.coplaydev.unity-mcp/Editor/Tools/Build/`. Файлы есть на диске у тебя локально, но **не закоммичены** → чистый checkout на сервере их не получает → namespace не существует. Диагностика: `git check-ignore -v <путь>` и `git ls-files <папка>` (пусто = не отслеживается). Лечение: точечное исключение в `.gitignore` (`!Packages/.../Build/`) + `git add -f`. Проверить разом: `find Packages Assets -type d -iname build | while read d; do git check-ignore -q "$d" && echo "IGNORED: $d"; done`.
> 2. **Платформенный модуль/пакеты не установлены на сборочной машине.** namespace вроде `UnityEngine.InputSystem.PS5` (PS5 Platform-модуль Unity, NDA) существуют только когда соответствующие пакеты доставлены на сервер. (`Plugins.UpscaleSDK.PS5.Runtime.*` — PS5-модуль Upscale SDK — с SDK v2.1 едет в комплекте пакета и лежит в репо, но его `#if UNITY_PS5`-код всё равно компилируется только при установленных Unity-пакетах платформы.) На ноуте под Standalone `#if UNITY_PS5`-блоки выключены — поэтому локально чисто. **Перед написанием `using` на платформенные типы — сверять фактический namespace grep'ом по установленному пакету, НЕ угадывать** (детали и точные namespace по платформам — `UPSCALE_SDK.md`, раздел Platform).

> ⚠️ **Подводный камень: после чистки SDK остаётся тихий `NullReferenceException` в `Start()`, и часть инициализации молча не доезжает.** Причина: кнопку/объект удалили из префаба (поле в компоненте стало `{fileID: 0}`), а код обращается к нему безусловно. Плейтестом не ловится — подписки выше уже навесились, UI работает и показывает данные; оборвавшийся хвост метода часто дублируется событием, так что видимого симптома нет. Найдено в `TopBarCanvas.SetButtons()` спустя пять стадий после чистки (2026-07-31): `removeAdsButton.onClick.AddListener(...)` при пустой ссылке рушил метод, из-за чего не вызывался `DoubleSpeedBtnActiveStatus()` — состояние кнопок скорости (а с ними и подсказка «Speed x2») выставлялось не при старте, а только после следующего `OnTutorialStepUpdate`.
>
> **Лечение:** `if (field) { ... }` вокруг подписки — или выпилить поле вместе с логикой, если механика удалена. **Поиск всех таких мест** — процедура в `STAGE-1-SDK-CLEANUP.md`, раздел «Обязательная сверка: обнулённая ссылка в префабе ↔ безусловное обращение в коде»: `grep ": {fileID: 0}"` по правленым префабам, затем по каждому полю проверить, нет ли обращения без guard. Пустая ссылка сама по себе нормальна (в том же `TopBarCanvas` `leaderBoardButton` и `offersButton` остались только в закомментированных строках) — опасно именно безусловное обращение.
>
> **Отдельно помнить:** консоль в этом проекте постоянно шумит (`Compatibility Mode`, GUID-warning'и про `.meta`), поэтому одну строку NRE в ней легко не заметить — читать `read_console types=error` **со стеком** и разбирать каждое исключение из `Start`/`Awake`/`OnEnable`.

> ⚠️ **Подводный камень: подсказки Apply/Cancel инвертируются на Switch, если глиф задан позицией кнопки.** 🕓 **СТАТУС: правка внесена 2026-07-31, на девките НЕ ПРОВЕРЕНА** — подтвердить и снять пометку после теста (ожидаем: «Pick» показывает **A**, «Leave» — **B**).
>
> **Симптом:** на Switch подсказка на подтверждение рисует B, а срабатывает A; на отмену рисует A, а срабатывает B. Остальные глифы (R3, DPad, ZL/ZR, шифты) верные, поэтому при быстром осмотре билда всё выглядит нормально.
>
> **Причина — рассинхрон двух половин.** Ввод был сделан правильно, на семантических экшенах: `PlayerInputActionSet` биндит `action: GamepadAction.Apply` / `GamepadAction.Cancel`, `BaseGamepadActionSet.Instance.Apply` в модалках. SDK сам разводит их по платформе — `GamepadActionSource.GetButtonForApply()`: `Nintendo → ButtonEast (A)`, `PlayStation/Xbox → ButtonSouth`; `GetButtonForCancel()` зеркально; на PS4 ещё учитывается системный Cross-as-Enter. А подсказки (`PromptDefs`) задавали глиф **позиционно** — `GamepadGlyph.South` для подтверждения, `East` для отмены. Наборы глифов при этом замаплены физически корректно (`Switch Colored IconsSet`: `East → button_switch_digital_a`, `South → button_switch_digital_b`), поэтому позиционный глиф на Switch и даёт противоположную кнопку.
>
> **Лечение (внесено):** `PromptDef` получил `PadAction`/`HasPadAction` + конструкторы от `GamepadAction`; `GlyphResolver.GetActionGlyph(action, fallback)` берёт спрайт через `GamepadActionSource(action, Press).GetGlyph(GlyphProvider)` — кнопку выбирает SDK; `PromptRow` использует экшен, если он задан. В `PromptDefs` переведено 28 определений на `Apply` и 6 на `Cancel`; позиционные (`West`/`North`/шифты/триггеры/DPad/стики/`RightStickButton`) оставлены — по вводу они тоже позиционные, так что совпадают везде. Фолбэк-глиф считается по смыслу (`Apply→South`, `Cancel→East`), а не через `default`: у enum `GamepadGlyph` первое значение `North`, и `default` дал бы иконку X. Вызов обёрнут в try/catch: без поднятого `UPSInput` (в билде `GetGamepadType()` обращается к `_instance._inputProvider`) резолв кинул бы NRE.
>
> **ПРАВИЛО НА БУДУЩЕЕ (для любого проекта):** подтверждение/отмена в подсказках **никогда** не задаются позицией кнопки (`South`/`East`) — только семантическим экшеном, глиф спрашивается у SDK. Позиция допустима лишь там, где и биндинг позиционный (`ButtonWest`, `ButtonNorth`, шифты, триггеры, DPad, стики). Проверка одной командой: `grep -n "GamepadGlyph.South)\|GamepadGlyph.East)" <файл с определениями подсказок>` — должно быть пусто.
>
> **Дальше (не сделано):** у SDK v2.1 есть device-aware `action.Press.TryGetGlyph()` — он идёт по источникам биндинга и отдаёт спрайт под активное устройство. Если ссылаться в определении подсказки прямо на `InputAction` из `PlayerInputActionSet`, то ни геймпадный, ни клавиатурный/мышиный глиф дублировать в таблице вообще не придётся, и рассинхрон станет невозможен по построению. Это переработка всех определений — отдельной задачей.
>
> **После подтверждения на девките:** перенести «правило на будущее» в `UPSCALE_SDK.md` (раздел про глифы, рядом с описанием `ProvideGamepadSet`) и в `STAGE-2-5-GAMEPAD-UI.md` (как требование при проектировании подсказок), чтобы в следующих проектах не повторять.

> ⚠️ **Подводный камень: Switch-билд падает на линковке `undefined symbol: nn::...` — устаревший NintendoSDKPlugin.** Симптом (словлено 2026-07-30): `ld.lld: error: undefined symbol: nn::err::ErrorCode::IsValid() const`, `referenced by err_Types.cpp ... in archive Assets/UpscaleSDK/Platform/Switch/NintendoSDKPlugin/NintendoSDKPlugin.a`, дальше `clang++: linker command failed`. Выглядит как ошибка кода или UpscaleSDK — но ни то, ни другое: C#-биндинг `nn/err/err_Types.cs` объявляет `DllImport nn_err_ErrorCode_IsValid`, C-обёртка лежит в `NintendoSDKPlugin.a`, а она вызывает C++-метод из библиотек **установленного NintendoSDK**. Если плагин собран под другую версию SDK/Unity — символа нет.
>
> **Лечение:** обновить `NintendoSDKPlugin` (папку `Assets/UpscaleSDK/Platform/Switch/NintendoSDKPlugin/` целиком — `.a` + `.dll` + `nn/`, они версионно связаны) на сборку под текущую версию Unity. Плагин обновляется часто, отдельно от репозитория, и версия жёстко привязана к версии редактора.
>
> **Диагностика, не выходя из проекта:** под какую версию Unity собран архив, видно в зашитых путях сборки — `strings -a NintendoSDKPlugin.a | grep "JW/workspace"` выдаёт что-то вроде `D:/JW/workspace/Unity6000.0/Plugins/NintendoSDKPlugin/Sources/...`. Если мажор/минор не совпадает с `ProjectSettings/ProjectVersion.txt` — это оно.
>
> **Обходить вырезанием биндингов нельзя.** Линкер называет только первое вхождение; на `nn::err::ErrorCode::IsValid` в архиве ссылаются четыре объекта — `err_Types.o`, `err_ShowErrorApi.o`, `ec_ConsumableServiceItemApi.o`, `ec_ShopServiceAccessor.o`. Чтобы убрать ссылки, пришлось бы удалить `nn.err` и `nn.ec` (системные диалоги ошибок + магазин/IAP). Проверить состав ссылок можно распаковкой архива (`ar`) и поиском mangled-символа `_ZNK2nn3err9ErrorCode7IsValidEv` по объектам. Настройки asmdef (`UpscaleSDK.Platfrom.Switch`, `NintendoSDK` — оба `includePlatforms: [Editor, Switch]`) на эту ошибку не влияют вообще: падает линковка нативного кода, а не компиляция C#.

> ⚠️ **Подводный камень: Odin ломает консольный билд, а дефайн-лечение сам же стирает.** На PS5-сборке падает `Modules/Unity.Localization/Runtime/LocalizedStringFormatter.cs` с `CS0246` на `RegisterFormatter` / `ReflectionOrEmittedBaseFormatter<>` / `IDataReader`. Причина: платформенные списки в `.meta` у Odin написаны до появления PS5 — в `Assemblies/NoEditor/` и `Assemblies/NoEmitAndNoEditor/` у `Sirenix.Serialization.dll` стоит `Any: enabled 0` плюс поимённый перечень (Standalone/Android/WebGL/Linux…), где PS5 нет вообще, а корневая `Sirenix.Serialization.dll` — Editor-only. Итог: для PS5 не подключается ни одна. `Sirenix.OdinInspector.Attributes.dll` имеет `Any: enabled 1`, поэтому атрибуты компилируются и ошибок не дают. Xbox словит то же самое (`Exclude XboxOne: 1`).
>
> **Лечение:** включить Odin Editor Only Mode — **только** через `Tools → Odin → Serializer → Preferences`. Вписывать `ODIN_INSPECTOR_EDITOR_ONLY` руками в Player Settings бесполезно: `EditorOnlyModeConfig.EnsureEditorOnlyModeDefine` (в `Sirenix.OdinInspector.Editor.dll`) синхронизирует дефайн со своим конфигом и после ближайшей перекомпиляции удаляет строку. Режим безопасен: рантайм-сборка модуля отваливается по `defineConstraints: ["!ODIN_INSPECTOR_EDITOR_ONLY"]`, остальные модули (Addressables, Mathematics) и так `includePlatforms: ["Editor"]` либо целиком под `#if UNITY_EDITOR`. Odin-сериализация в игре не используется — во всём `Assets` вне самого Sirenix единственная зависимость это `[BoxGroup]` в `Assets/Vendor/Essentials/SpellOp/Shared/SpMonoBehaviour.cs`, ни `SerializedMonoBehaviour`, ни `SerializedScriptableObject` нет. Альтернатива без Odin-автоматики — удалить `Modules/Unity.Localization/Runtime/` (форматтер + asmdef, два файла).

> ⚠️ **Подводный камень: половина namespace'ов Input System существует не на всех платформах.** `UnityEngine.InputSystem.Switch` объявлен под `#if UNITY_EDITOR || UNITY_STANDALONE_WIN || UNITY_STANDALONE_OSX || UNITY_STANDALONE_LINUX || UNITY_WSA` (первая строка `SwitchProControllerHID.cs` в пакете) — на PS5 `using` этого namespace даёт `CS0234`, хотя локально под Standalone всё компилируется. `DualShock` и `XInput` таких гардов не имеют и доступны везде. Словлено на `Assets/Scripts/Input/Prompts/GlyphResolver.cs`: `using` и ветка `gp is SwitchProControllerHID` завёрнуты в тот же гард, что стоит в пакете.
>
> **Правило:** перед `using UnityEngine.InputSystem.<Платформа>` — открыть соответствующий файл в `Library/PackageCache/com.unity.inputsystem@*/InputSystem/Plugins/<Платформа>/` и посмотреть гард в первой строке; повторить его у себя. Заодно: на консоли определять тип пада через `#if UNITY_PS4 || UNITY_PS5 → GamepadType.PlayStation` вместо цепочки `is`-проверок — платформенный `UnityEngine.InputSystem.PS5.DualSenseGamepad` не обязан наследовать HID-шный `DualShockGamepad`, иначе fallback выдаст глифы Xbox на PS5.

> ⚠️ **Подводный камень: HighlightPlus не компилируется под PS5 (`sampler` не тип в PSSL) — правка плагина, теряется при обновлении.** На первой PS5-сборке (2026-07-30) шесть шейдеров плагина падали с `Shader error ... identifier 'sampler' is not a valid type` + `Invalid declaration. Found unexpected token: '_MainTex'` (on `ps5_nggc`). Причина: устаревшее объявление `sampler _MainTex;` (тип без размерности) — для D3D11/GLES проходит, компилятор PSSL его не знает. Объекты с `HighlightEffect` при этом рендерятся error-шейдером, т.е. **розовеют**, а сам билд собирается — ошибка не блокирующая и легко теряется в логе.
>
> **Лечение:** `sampler _MainTex;` → `sampler2D _MainTex;` в `Assets/3rd Party/HighlightPlus/Resources/HighlightPlus/`: `HighlightGlow` (61), `HighlightOutline` (58), `HighlightInnerGlow` (55), `HighlightSolidColor` (33), `HighlightUIMask` (37), `HighlightMask` (16). Использование не меняется (`TRANSFORM_TEX` + `tex2D` корректны для `sampler2D`), на Standalone/Android/WebGL поведение прежнее. Остальные шейдеры плагина (`HighlightSeeThrough*`, `HighlightTarget`, `HighlightOverlay`) уже объявлены через `sampler2D` — правка приводит файлы к стилю самого плагина.
>
> **Это патч стороннего плагина** — при переустановке HighlightPlus из Asset Store он молча пропадёт. Проверять после каждого обновления: `grep -rn "sampler _MainTex;" "Assets/3rd Party/HighlightPlus"` — должно быть пусто. Отдельно помнить: рендер HighlightPlus вообще требует URP Compatibility Mode (Render Graph disabled), дефайна `URP_COMPATIBILITY_MODE` для этого недостаточно — он только про компиляцию C#-части плагина.

> ⚠️ **Подводный камень MCP + Prefab Stage:** если пользователь держит префаб открытым в Prefab Stage в редакторе, операции `PrefabUtility.LoadPrefabContents` + `SaveAsPrefabAsset` (а также `manage_prefabs.modify_contents`) **молча отваливаются** — файл на диске не меняется, `mtime` остаётся прежним. В консоли Unity при этом стоит ошибка `Failed to save prefab asset`, но это легко пропустить. Перед массовыми правками префабов:
> 1. Попроси пользователя закрыть открытый Prefab Stage (стрелка `<` → **Don't Save** если есть несохранённые правки), иначе они затрут твои изменения.
> 2. После своих правок проверь `mtime` через `stat -f "%Sm" path.prefab` — если время не изменилось, правка не сохранилась.
> 3. Альтернативно — программно закрыть stage через `manage_prefabs.close_prefab_stage` перед началом массовой работы, но это работает только если stage был открыт через MCP.
>
> ⚠️ **Подводный камень: "script does not derive from MonoBehaviour":** Unity отказывается сохранять префаб с компонентом, чей `m_Script` GUID указывает на файл, **существующий** (`.cs`+`.meta` есть, GUID валидный), но **компилируемый в null-класс** (например, весь файл закомментирован `/* ... */`). Это **не** missing-script — `RemoveMonoBehavioursWithMissingScript` его не подхватит. `GetComponents<Component>()` возвращает `null` для этого slot, но `m_Component[i].component.objectReferenceValue != null` (ссылается на MonoScript-ассет). **Диагностика:**
> ```csharp
> var rx = new System.Text.RegularExpressions.Regex(@"m_Script:\s*\{fileID:\s*\d+,\s*guid:\s*([0-9a-fA-F]+),");
> foreach (Match m in rx.Matches(prefabYaml)) {
>     var path = AssetDatabase.GUIDToAssetPath(m.Groups[1].Value);
>     var mono = AssetDatabase.LoadAssetAtPath<MonoScript>(path);
>     if (mono != null && mono.GetClass() == null) Debug.Log("BROKEN: " + path);
> }
> ```
> **Лечение:** найти `.cs` файл (через `AssetDatabase.GUIDToAssetPath` или grep `.meta`-файлов на guid). Либо вернуть в файл валидный класс (раскомментировать), либо **удалить `.cs` + `.meta`** целиком — тогда компоненты на префабах становятся честно missing-script и `RemoveMonoBehavioursWithMissingScript` их вычистит.
>
> ⚠️ **Подводный камень: двойные nested UI-элементы (CurrencyBar / TopBar и т.п.):** один и тот же UI-префаб (например `CurrencyBar.prefab`) часто используется **в нескольких местах** — на HUD-канвасе, во вкладке магазина, в Pause-меню. Если правишь его через `LoadPrefabContents` на одном из родителей (например ShopUI), Unity создаёт **override на nested instance**, который потом легко переписывается обратно при обновлении исходного префаба. Это приводит к расхождениям между копиями.
>
> **Правило:** всегда правь **исходный nested-prefab**, не override на родителе. Чтобы найти где живёт исходный — `manage_prefabs get_hierarchy` на родителе → у nested-узлов в `prefab.isNestedRoot == true` указан `prefab.assetPath` исходника. Открой именно его и правь там — изменения автоматически пропагируются во все instance'ы.
>
> ⚠️ **Подводный камень: Nested Prefab AddedGameObject override:** иногда узел физически живёт **в инстансе как AddedGameObject override**, а в исходном nested-prefab его нет. Например: кнопка `Close_Btn` лежит в `MainCanvas.prefab` без дочерних объектов, но в `ShopUI.prefab` под ней есть дочерний `Text "AD"`, добавленный как override. При попытке удалить `Text` через `LoadPrefabContents("MainCanvas.prefab")` ты ничего не найдёшь, а изменения в `ShopUI.prefab` через `modify_contents` `delete_child="MainCanvas/Area/Close_Btn/Text"` могут **молча не сработать** на nested-узлах. Решение: открой именно **тот префаб, в котором узел физически серилизован** (родительский, где он AddedGameObject), и делай `DestroyImmediate` через `execute_code` напрямую. Чтобы понять где узел — в YAML родительского префаба он будет рядом с блоком `--- !u!1001 PrefabInstance` (это маркер AddedGameObject).

> ⚠️ **Смена `companyName` под валидатор SDK теряет `PlayerPrefs`, а `defaults write` Unity не видит.** Валидатор требует `companyName == "Upscale Studio"`; на macOS `PlayerPrefs` живут в `~/Library/Preferences/unity.<company>.<product>.plist`, так что после переименования игра стартует «новой», а старые сейв/настройки разработчика остаются в `unity.DefaultCompany.<product>.plist`. Писать значения в новый plist через `defaults write` при работающем редакторе бесполезно: Unity держит свою копию домена в памяти и при следующем `PlayerPrefs.Save()` затирает файл (словлено 23.09.2026 на Sort Them — импорт в SDK-хранилище подхватил пустой сейв тестового запуска). Порядок: до смены имени `plutil -convert json` старого plist в бэкап; после — либо копировать plist при закрытом редакторе, либо класть данные сразу в файл SDK (`Application.persistentDataPath/UpscaleSaves/<XboxContainerName>.txt`, JSON: `Data[key] = сериализованное значение`, строки в кавычках) при остановленном Play. Разовый импорт `PlayerPrefs → UPSSaves.Prefs` в коде всё равно нужен для игроков.

> ⚠️ **SDK v2.1: `UPSInput.GetGamepadType()` кидает NRE на геймпаде без описания устройства.** `NewUnityInputProvider.GetGamepadType` (строка ~211) делает `ActiveGamepad.description.manufacturer.ToLower()` / `.product.ToLower()` без проверки на null. Словлено 24.09.2026 на виртуальном `InputSystem.AddDevice<Gamepad>()` в тесте; у реального DualSense поля заполнены. Может стрелять на ПК с экзотическими HID-падами и в автотестах. Обход в игре — все обращения к глифам SDK завёрнуты в try/catch (`GameAction.Glyph`), сообщить вендору. Для тестов создавать пад через `AddDevice(new InputDeviceDescription { interfaceName = "Test", deviceClass = "Gamepad", manufacturer = "…", product = "…" })`.

> ⚠️ **Addressables кэширует `[BuildTarget]` в статике: сборка под платформу B после сборки под A в той же сессии редактора получает каталог с путём `aa/<A>/`.** Симптом: в билде локализация не грузится (`RemoteProviderException: Unable to load asset bundle ... aa/StandaloneWindows64/...`, потом каскад `SelectedLocale is null`), хотя папка `StreamingAssets/aa/<B>/` с бандлами на месте. Причина: `AddressablesRuntimeProperties` кэширует вычисленное `[UnityEditor.EditorUserBuildSettings.activeBuildTarget]`, `BuildPlayerContent` во время сборки игрока кладёт бандлы в `Library/com.unity.addressables/aa/<A>/`, а в билд копирует `aa/<B>/` со старыми бандлами и новым каталогом. Лечение в скрипте сборки перед `BuildPlayer`: `EditorUserBuildSettings.SwitchActiveBuildTarget(...)` при несовпадении, затем `AddressablesRuntimeProperties.ClearCachedPropertyValues()` и проверка `settings.profileSettings.EvaluateString(activeProfileId, "[BuildTarget]")`; при расхождении — `BuildFailedException`. 📍 Sort Them: `Editor/BuildTool.EnsureWebGLTarget()`. При консольных сборках с одной машины (PS5 → Switch → Xbox подряд) это будет стрелять постоянно.

> ⚠️ **Рантайм-материал через `Shader.Find` — на консоли объект может быть НЕВИДИМ.** `new Material(Shader.Find("Universal Render Pipeline/Lit"))` в редакторе и в ПК-билде рисуется всегда: там доступны все варианты шейдера. В консольном билде (проверено на Switch) шейдерные варианты собираются только под то, что реально используют материалы-ассеты в билде, поэтому рантайм-материал может остаться без собранного варианта — и меш не рисуется **вообще**, без розового «error shader» и без ошибки в консоли. Симптом путает: объект на месте (коллайдер работает, HighlightPlus рисует аутлайн), а геометрии не видно.
>
> Так проявился баг кастомных футболок: `DesignStorage.GetMaterial` собирал материал дизайна с нуля на URP/Lit, хотя **вся одежда в игре — URP/Simple Lit**. На ПК всё рисовалось, на Switch у кастомных вещей пропадала ткань на вешалке и внутри пакета (пакет, ценник и наклейки при этом были видны — у них свои материалы).
>
> **Правило:** рантайм-материал получать **клонированием материала-ассета, который уже лежит на объекте в билде** (`new Material(template)`), и подменять только текстуру/цвет. Клон наследует шейдер вместе с набором keywords, вариант гарантированно собран, плюс освещение совпадает с остальным контентом. `Shader.Find` оставлять только запасным путём с явным `LogWarning`. Альтернатива (грубее) — Always Included Shaders / ShaderVariantCollection в Preloaded Assets.
>
> **Как проверить, попадёт ли шейдер в билд:** собрать список материалов из `EditorBuildSettings.scenes` + всего, что лежит в `Resources/` (через `AssetDatabase.GetDependencies`), и посмотреть, есть ли среди них нужный шейдер с нужными keywords. Наличие материала где-то в `Assets/` ничего не гарантирует — папки Demo/примеры в билд не идут.
>
> **Статус:** исправлено 2026-08-04 (`DesignStorage.GetMaterial(index, template)` + `LoadCustomDesignData.GetClothTemplateMaterial()`), **на девките ещё НЕ проверено**.

> ⚠️ **TMP: статический атлас «ровно из текста таблиц» теряет прописные.** `FontStyles.UpperCase`/`SmallCaps` и тег `<uppercase>` меняют регистр при рендере, а в таблицах буквы чаще строчные — в атлас попадает `й`, но не `Й`, и заголовок «НАСТРОЙКИ» рисуется с квадратом. Правило: в набор символов для атласа класть `ToUpperInvariant` и `ToLowerInvariant` каждого символа. 📍 Sort Them: `Editor/FontAtlasTool.Chars()`.

> ⚠️ **TMP: пересборка статического атласа на месте (Dynamic → добавить символы → Static) не трогает материал.** Если атлас вырос (1024² → 2048²), `_TextureWidth/_TextureHeight` в материале остаются старыми — выставлять руками по `atlasTexture.width/height`. Также: `TMP_FontAsset.atlasWidth/atlasHeight` только для чтения — менять через `SerializedObject` (`m_AtlasWidth/m_AtlasHeight`); `m_SourceFontFile_EditorRef` приватный, а `FontEngineEditorUtilities.SetAtlasTextureIsReadable` internal — оба через reflection. Глоу/underlay в SDF-шейдере зависит от соотношения padding/pointSize: у всех шрифтов проекта держать одно соотношение (86/9 ≈ 64/7), иначе одинаковые `dilate/softness` дадут разную толщину. 📍 `Editor/FontAtlasTool.cs`.
