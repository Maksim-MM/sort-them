# Скилл `/unity-analyze` — установка и исходник

Этот файл едет вместе с китом `porting/`. По нему любой разработчик ставит себе команду `/unity-analyze` — отдельной инфраструктуры не нужно: создаёшь один файл и вставляешь в него тело из раздела «Исходник» ниже.

## Что это и когда запускать

`/unity-analyze` — это **Stage 0** пайплайна. Команда изучает Unity-проект через MCP и генерит:
- `CLAUDE.md` — инструкции проекта + порт-станза с триггер-словами;
- `ARCHITECTURE.md` — карту проекта (сцены, иерархии, системы, SDK);
- `PROGRESS.md` — заготовку лога порта по стадиям.

> ⚠️ Запускать только на **зелёной сборке** (Editor без ошибок компиляции, MCP отвечает) — см. `README.md` §3. По сломанному проекту анализ бессмыслен.

## Как установить у себя

- [ ] **Вариант 1 (рекомендуется) — личная команда.** Создай файл `~/.claude/commands/unity-analyze.md`
      (Windows: `%USERPROFILE%\.claude\commands\unity-analyze.md`) и вставь в него **всё тело** из раздела «Исходник» ниже. Команда заработает во всех твоих проектах.
- [ ] **Вариант 2 — проектная команда.** Тот же файл, но в `<репозиторий>/.claude/commands/unity-analyze.md` — доступна только в этом проекте. (Учти: в наших порт-проектах `.claude/` обычно в `.gitignore`, т.е. через git не разъедется.)
- [ ] **Имя файла = имя команды:** файл `unity-analyze.md` → команда `/unity-analyze`.
- [ ] **Проверка:** в Claude Code набери `/unity-analyze` — команда должна появиться в автодополнении.

**Примечания:**
- В актуальном Claude Code команды и скиллы равнозначны — можно положить и как `~/.claude/skills/unity-analyze/SKILL.md`, эффект тот же. Любые другие личные скиллы передаются этим же способом.
- Опционально в начало файла можно добавить frontmatter (`--- description: ... ---`) — но для работы команды он не обязателен.

## Исходник команды (копировать целиком)

Скопируй **всё между внешними четырьмя бэктиками** в свой файл `unity-analyze.md` — это рабочее тело команды как есть. Внутренние блоки на тройных бэктиках (примеры `CLAUDE.md` и `.gitignore`) — часть исходника, их тоже копируем.

````markdown
Ты помогаешь изучить Unity-проект и подготовить его к портированию на консоли: создать документацию по архитектуре и развернуть рабочие порт-документы (Stage 0 порт-пайплайна).
Общайся и пиши всю документацию на русском языке.

Выполни следующие шаги по порядку:

## Шаг 0 — Префлайт: проект должен компилироваться

Перед анализом убедись, что Editor без ошибок компиляции: `mcp__UnityMCP__read_console (types=[error])` + поле `editor_state.isCompiling`. Если есть ошибки компиляции — **останови анализ** и сообщи пользователю: сначала чиним сборку (версия Unity, битые рефы, пакеты), по сломанному проекту MCP не отдаёт сцены и анализ бессмыслен. Это отдельная задача до Stage 0.

## Шаг 0.5 — Папка porting/

Проверь наличие папки `porting/` в корне проекта (там живёт кочующий порт-пайплайн: `PORTING_PIPELINE.md` — индекс, файлы стадий `STAGE-*.md`, `GOTCHAS.md`, `UPSCALE_SDK.md`, `MCP_REFERENCE.md`).
- Если папки нет — попроси пользователя скопировать её из предыдущего порт-проекта и дождись, пока он это сделает. Сам содержимое не выдумывай.
- Если есть — прочитай только `porting/PORTING_PIPELINE.md` (индекс) и `porting/STAGE-0-ANALYSIS.md`: это спецификация того, что искать на этапе анализа.

## Шаг 1 — Сцены

Используй `mcp__UnityMCP__manage_scene` с `action: get_build_settings` чтобы получить список всех сцен.
Затем для каждой сцены:
- Загрузи иерархию через `get_hierarchy` с `max_depth: 2`
- Для объектов с важными скриптами (контроллеры, менеджеры, UI, персонажи, игрок) углубись ещё на 2-3 уровня
- Объекты с пометками Environment, Props, City, Terrain, Decor — просто упомяни как "окружение/пропсы", иерархию не разворачивай
- Ноды навигации (RoadNode, Waypoint, Path) — упомяни количество, не разворачивай

## Шаг 2 — Скрипты и архитектурные паттерны

Не предполагай конкретные имена файлов — у каждого проекта своя архитектура. Ищи паттерны (папки Plugins, Vendor, Editor, BuildReport, сторонние ассеты — не трогай):

- **Точки входа**: корневые объекты сцены с индексом 0 и их компоненты; что они инстанцируют дальше (бутстрап-цепочка). `DontDestroyOnLoad`-объекты.
- **DI-контейнер**: поищи (`*Injector*`, `*Container*`, `*Installer*`, Zenject/VContainer в Packages), но не предполагай, что он есть — часто его нет.
- **Шина событий**: `grep -rn "static.*Action\|static event" Assets/Scripts` — глобальные события могут жить в одном файле, в partial-классе на много файлов или вообще отсутствовать.
- **Глобальное состояние / сейвы**: `PlayerPrefs`, `JsonUtility`, `*Saving*`, `*SaveData*`, `*DB*` — где хранится прогресс и кто его пишет.
- **Стейт-машины**: папки/файлы с `State` в названии, abstract-базы с наследниками.
- **Синглтоны**: `grep -rn "static.*\(ins\|instance\)" Assets/Scripts`.
- **Захардкоженные Resources-пути** (критично для порта — молча ломаются при переносе ассетов): `Resources.Load`, `[SerializeField] string` с путями (`*ResPath`, `*Path`). Зафиксируй каждый: какой компонент, какая строка, какой префаб грузится.
- Основные контроллеры (суффикс `Controller`), скрипты игрока, движение, магазин и экономика — по факту обнаружения.

## Шаг 3 — Мобильные и платформенные SDK

Найди всё специфичное для мобильных/веб платформ:
- Поищи папки: `find Assets -maxdepth 3 -type d | grep -iE "admob|firebase|google|ads|iap|purchase|analytics|adjust|appsflyer|facebook|applovin|ironsource|consent|gdpr"`
- Проверь `Packages/manifest.json` на наличие аналитики и рекламных пакетов
- Найди `google-services.json` и похожие конфиги
- Тач-ввод: Control Freak, TouchControlsKit, `Input.touches`, `isMobilePlatform`-разводки
- Для каждого найденного SDK определи: активен ли он реально или это заглушка/закомментированный код

## Шаг 4 — Создай документацию

### CLAUDE.md
Создай или перезапиши `CLAUDE.md` в корне проекта. Включи:
- **Порт-станзу первым разделом** (как в примере ниже): триггер-слова → `porting/PORTING_PIPELINE.md` (индекс) → файл нужной стадии
- Описание игры (жанр, платформы, механики)
- Ключевые сторонние плагины с путями
- Архитектурные паттерны — те, что реально нашёл на Шаге 2 (и явно перечисли, чего в проекте НЕТ: нет DI, нет единой шины и т.п. — чтобы не искали)
- Основные системы и как они связаны
- ScriptableObjects и синглтоны
- Захардкоженные Resources-пути и прочие особенности, неочевидные из кода

Начни файл с:
```
# CLAUDE.md

Этот файл содержит инструкции для Claude Code (claude.ai/code) при работе с данным репозиторием.

## Порт на консоли — рабочие документы (читать первыми)

Если задача касается порта на консоли / геймпада / контроллера: **триггер-слова** — порт, консоль, геймпад, контроллер, gamepad, SDK, UpscaleSDK, сохранения/сейвы, глиф, hotkey/хоткей, Layer/слой, вибрация.

При любом из них **сначала прочитай** `porting/PORTING_PIPELINE.md` — это **индекс**: по его таблице маршрутизации определи файл нужной стадии (`porting/STAGE-*.md`) и читай **только его**, не всю папку. Дополнительно по ситуации: `porting/GOTCHAS.md` — перед любой работой с префабами/сценами через Unity MCP; `porting/UPSCALE_SDK.md` — при работе с геймпадом/сейвами/глифами.

Карта проекта — `ARCHITECTURE.md`; что уже сделано по порту — `PROGRESS.md`.
```

### ARCHITECTURE.md
Создай `ARCHITECTURE.md` в корне проекта. Включи:
- Таблицу сцен (index, путь, назначение)
- Иерархию каждой сцены с описанием ключевых объектов
- Управление (ввод, камера, кнопки действий)
- Жизненный цикл основной игровой механики (полный поток вызовов)
- Структуру HUD
- Таблицу глобальных событий (кто стреляет → кто слушает)
- Граф зависимостей / бутстрап-цепочку
- Таблицу SDK (название, статус: активен/заглушка/закомментирован, что вырезать при порте)
- Таблицу захардкоженных Resources-путей

### PROGRESS.md
Если `PROGRESS.md` нет — создай заготовку: заголовок со статусом порта («Stage 0 — анализ, <дата>»), по секции на каждую стадию из `porting/PORTING_PIPELINE.md` (пустые, с пометкой «не начато»). В секцию Stage 0 сразу запиши результат анализа: какие стадии применимы к этому проекту, какие пропускаем и почему.

## Шаг 5 — Проверь .gitignore

Убедись что в `.gitignore` есть строки:
```
CLAUDE.md
ARCHITECTURE.md
PROGRESS.md
porting/
.claude/
```
Если нет — добавь. (Учти: при работе с нескольких машин gitignored-доки не синхронизируются через git — их нужно копировать руками.)
````
